## 3. Locating ctm-libs and the shipped copy (E2)

The byte-identical bootstrap gets one optional argument. Messages for components without `opts.standalone` stay as they are (tests assert them).

```lua
-- ctm-libs bootstrap/ctm-bootstrap.lua: INSTALL, API, exists, candidates, find unchanged.
-- opts.standalone: the component also works without the package (decision 5);
--   the value is its own install command. opts.api: the ctm-libs interface
--   level the component needs (default API).
return function(component, opts)
  opts = opts or {}
  if not opts.standalone and os.getenv("CTM_COMPONENT_DEV") ~= "1" and not find("ctm-assessment", "_extension.yml") then
    assert(false, component .. " is part of CTM Assessment, which is not installed in this project. Install CTM Assessment: " .. INSTALL)
  end
  local again = opts.standalone and (" Install " .. component .. " again: " .. opts.standalone)
  local dir = find("ctm-libs", pandoc.path.join({"lua", "ctm.lua"}))
  assert(dir, again and (component .. " needs its library ctm-libs, which is missing next to it." .. again)
    or (component .. " is part of CTM Assessment and needs its library ctm-libs, which is not installed. Install CTM Assessment: " .. INSTALL))
  local ctm = dofile(pandoc.path.join({dir, "lua", "ctm.lua"}))
  assert(ctm.api >= (opts.api or API), component .. " needs a newer ctm-libs than " .. dir .. " (" .. ctm.version .. ")."
    .. (again or (" Update CTM Assessment: " .. INSTALL)))
  return ctm
end
```

`qpyodide.lua` loads it once at the top: `local ctm = dofile(quarto.utils.resolve_path("ctm-bootstrap.lua"))("pyodide-interaktiv", {standalone = "quarto add Erasmus-CTM/pyodide-interaktiv"})`. New ctm-libs functions (`ctm.runtime.worker`, `ctm.settings.keys`) are feature-checked as in step 2 (step-2 §3.5: on an older ctm-libs the function is missing and the component stops with the same message). `docs/development.md:100-108` ("raise `ctm.api` and the `API` of the bootstrap together") becomes "raise `ctm.api`; the component passes `{api = n}`".

**The shipped copy.** `scripts/sync-ctm-libs.py <ctm-libs checkout>` copies `_extensions/ctm-libs/` and writes `.github/ctm-libs-source.json` (`{repository, commit}`); it also copies `bootstrap/ctm-bootstrap.lua` to `_extensions/pyodide-interaktiv/ctm-bootstrap.lua`. `--check` (workflow `ctm-libs.yml`, replacing `feedback.yml`) fetches the recorded commit and requires both to be equal. The recorded commit is a ctm-libs `main` commit when P3 merges. The package ignores the copy (`ships-copies`, §11). The copy is the only ctm-libs code in the repository; it is never edited by hand.

## 6. Feedback and builds without AI feedback (E3)

- The loader's module becomes `ctm.feedback`: the passes `markCallout`, `prepare` and the per-cell `selection`/`context` (`qpyodide.lua:877`, `:1544`, `:1769`) are the same functions the alias handed out (step-1 §2.6.4). The "feedback need" is still decided before callouts are marked (F-59): `pyodide: feedback` (default true) or an `.ai-feedback` activity on the page.

- Users of the subset: `ensurePyodide` (`pyodide-runtime.js:75-110`), `installModule` (`:159-179`, `globals.set` + `runPythonAsync`), step 2's ctm-checkers payload (the same two, step-2 §3.3), math-exercise (`loadPackage`), py-exercise (`loadPackagesFromImports`, `runPythonAsync`), `canStop`/`stop` (`restart`). `docs/api.md` states the contract; a test pins the proxy's keys.
- Step 5 starts the same worker from `ensurePyodide` on standalone pages, without a plugin.

### 7.4 D2: two stages (E7)

1. **Stage 1:** interpreter and shared buffers; with `pyodide: packages` set, micropip and those packages too (a check may import them; today it waited for them as well). Then `qpyodideReady`/`qpyodideInstance` resolve and `mainPyodide` is set.
2. **Stage 2:** the background steps run one at a time. Before each step the worker takes every queued command first, so a component's `loadPackage('sympy')` or check waits at most for the step in progress (matplotlib about 1 s on the fast CI profile, audit §3).
3. **Pyodide's own cells** (`runCell`) wait for stage 2 *before* they enter the queue, so the queue never waits on them (no deadlock). Run buttons, the "ready" status and the startup cells follow `proxy.whenSetup` instead of `mainPyodide`/`qpyodideReady` (`qpyodide-cell-classes.js:324-330`, `:812-817`, `qpyodide-cell-initialization.js:26-28`): the learner sees what she sees today.
4. `MPLBACKEND=AGG` in the worker's environment: a check that imports matplotlib before stage 2 gets the backend `PY_SETUP` would set.
5. A check that uses `requests` before `pyodide_http.patch_all()` would fail where today it waited; that step comes first and takes tens of milliseconds; no course check uses the network.
6. Restart (Stop without shared buffers): both stages again; pending commands are rejected as today.

Expected: the combined page's first math check drops from about 10.1 s towards math-exercise alone (5.6 s) plus at most one step (T8). Trade-off: a check started early delays startup and autorun cells by its own load (SymPy about 5.5 s); that is D2's choice.

### 18.5 D2: checks never wait behind the extra packages (S2; replaces §7.4)

**Why the first design waits.** Pyodide 0.28.3's `loadPackage` holds one package lock for its whole run, downloads included: `loadPackageInner` awaits `this._lock()` around `downloadAndInstall` for every package (`pyodide.asm.js`). A check's `loadPackage('sympy')` therefore waits until a background `loadPackage('matplotlib')` has downloaded everything. The combined page downloads about 13 MB more than math-exercise alone (audit §3: 23.6 against 10.2 MB). On the slow line that wait can last about a minute.

**How the worker avoids it** (ctm-libs `runtime/pyodide-worker.js`, worker side). This version follows the second review, after the browser measurements below:

1. **Stage 1, then `qpyodideReady`.** The worker loads:
   - the interpreter and the shared buffers;
   - the `input()` prompt hook, moved out of `PY_SETUP` because it needs no matplotlib;
   - when `pyodide: packages` is set, micropip and those packages (a check may import them; 1.8 waited for them too).
2. **Stage 2, downloads.**
   - The worker reads `pyodide-lock.json`, which start-up already put in the cache. It takes the closure of pyodide_http, micropip and matplotlib, minus `pyodide.loadedPackages`.
   - It downloads the wheels in byte ranges of 512 KB, one request at a time, smallest file first, from the URLs `loadPackage` will use (N5). It never holds Pyodide's package lock while doing so, and it never aborts a request.
   - ~~The browser keeps every finished range, and the later full requests of `loadPackage` come from the cache.~~ True of the measurement server below (strong ETag, `Accept-Ranges`), not of jsDelivr: with its wheel headers (a weak ETag, `Vary: Accept-Encoding`, no `Accept-Ranges`) Chromium does not serve the full request from cached ranges. Installs therefore take the prefetched bytes once they verify (item 3, 21 Oct).
   - Before each range the worker checks its queue. While a command that may download is queued or running, it waits, and it resumes 2 s after the last such command ends. A command "may download" when it is a `loadPackage`, or a `loadPackagesFromImports`, for a package not yet loaded.
   - Other commands (`runPython`, `setGlobal`) do not pause the prefetch, because they do not use the network.
   - So a check's download shares the line with at most the rest of one range (512 KB: at most 2.6 s at 1.6 Mbit/s).
   - Stage 2 cannot starve (N2): only a component's first package loads download anything, later checks never pause the prefetch, and an install waits at most 5 s for a pause in the commands (item 3).
3. **Stage 2, installs.** Once every range has arrived, the worker installs one package at a time, in dependency order, with `loadPackage(name)`, each only while nothing is queued or running and no command has ended for 300 ms (§18.14, S1: a check's calls are separate round trips, and without the quiet time an install would slip into each gap between them). **Ceiling (re-review S-a, 20 Oct):** an install waits for that quiet time for 5 s at most; then it takes the next moment nothing is queued or running (it never interrupts a command and never jumps the queue). Each install's 5 s count from the end of the one before. So under commands that never pause for 300 ms, installs are at least 5 s apart and stage 2 takes about 5 s per package (matplotlib's closure: about 75 s; measured in Chromium with a call every 100 ms: Ready after 79 s); a check shorter than 5 s meets at most one install; a longer check can meet one per 5 s, and an install can come right after a single call longer than 5 s (still one install for that check). Then comes `pyodide_http.patch_all()`. **Installs from verified bytes (set CI, 21 Oct):** the prefetch keeps the bytes; once a file's SHA-256 is the lock file's, the worker answers `loadPackage`'s request for that URL itself, and the Cache Storage `ctm-pyodide-wheels` keeps the wheel for the next page (the prefetch then bypasses the HTTP cache). With the real jsDelivr, whose wheel responses carry a weak ETag, `Vary: Accept-Encoding` and no `Accept-Ranges`, Chromium did not serve `loadPackage`'s full requests from the cached ranges, and in CI they failed ("pyodide-http: Failed to fetch"); the measurements below used a server with a strong ETag and `Accept-Ranges`. On a plain-HTTP origin (no `crypto.subtle`, no Cache Storage) nothing can be verified or kept: the prefetch fills the HTTP cache and `loadPackage` fetches as before. A wheel that does not verify is fetched by `loadPackage` as before. An install reads from memory and cannot be interrupted, so a check that arrives during one waits for that one package. The largest is numpy (measured below).
4. **The plot setup runs with the first Pyodide cell.** Importing `pyplot` is the longest step that cannot be interrupted: measured below, it takes as long as the interpreter's own start, or longer. So it leaves stage 2:
   - The first `runCell` (startup cells included) runs `PY_SETUP`'s plot part before the cell's code, inside that cell run.
   - A check therefore never waits for it as background work. It waits for a running cell, as it does today.
   - A page where no Pyodide cell runs never imports `pyplot`.
   - If the plot setup fails, `runCell` notes it, skips the figure collection and runs the code. `_qpyodide_collect_figures` exists only after `PY_SETUP` (N4).
5. **Pyodide's own cells.**
   - Run buttons and startup cells wait for stage 2, through `whenSetup` and a synchronous `qpyodideCellsReady` flag (§18.9).
   - The first Run then includes the plot setup, which today happens before Run is enabled.
   - `MPLBACKEND=AGG` is set in the worker's environment, so a check that imports matplotlib gets the backend `PY_SETUP` would set.
6. **Limits.**
   - Installs take the verified prefetched bytes (item 3), so neither a private window's in-memory cache nor the cache switched off in the developer tools matters any more.
   - A wheel that does not verify, and every wheel on a plain-HTTP origin, downloads inside Pyodide's lock when it is installed, and a check can wait for that one file.
   - Both are documented (ctm-libs `docs/api.md`).

**Failure and hang.** Stage 2 has its own limits; stage 1 keeps the 180 s load limit.
- **Prefetch:** a range with no bytes for 30 s is requested again after 5 s, then after 30 s; a third failure ends stage 2.
  - Requests are short ranges, never aborted on purpose: an abort does not stop a transfer that goes through the COI service worker (measured below).
  - There is no total limit: a slow line may need minutes, and progress is what counts.
- **Install:** it downloads nothing, so it cannot stall on the network. An install longer than 60 s is reported in the status line; Stop restarts the worker, as today.
- **On failure** `whenSetup` rejects:
  - Pyodide's status line shows a new catalogue text with a Retry button; the text names the effect (AC, 20 Oct), in the catalogue's own words for "unaffected" (re-review S-b): "🟠 Plots are not available: some packages could not be loaded (matplotlib: HTTP 404). Other Python code works normally." The reason names the package once, without the URL, which goes to the console (m2). Retry repeats the missing steps without restarting Python.
  - The Run buttons are enabled: code without matplotlib runs, and a cell that imports it shows the error in its output. Today any start-up failure leaves no cell usable (`engineFailed`).
- **Checks** never depend on stage 2. A restart (Stop without shared buffers) runs both stages again. It also rejects the old start's `whenSetup` (`error.restarted`), and calls on the old proxy reject at once (§18.14, B1).
- **New strings:** the failure text and "Retry", in en, de, sv, nb and da; AC reviews the wording, as in step 4.

**Measured in Chromium** (second review: real browsers, not Node). Setup:
- Chromium 141 (Playwright 1.55, the full browser in `/opt/pw-browsers`), headless, with an on-disk profile like a normal browser, and once with an in-memory profile, like a private window.

- The scripts and results of the design session are not kept; T3 and T8 (below) repeat the measurements in CI.
