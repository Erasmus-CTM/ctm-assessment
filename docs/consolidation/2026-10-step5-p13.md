## 1. Outcome and phase boundary

The primary deliverable is a **Pyodide-only Python IDE for exams**, based on
the two existing [offline Python website ZIP](../exam-site-zip.md) pages in
integration/offline-ide. It runs in SEB, supports Run, Stop and stop-after,
and keeps the page usable while Python loops. It retains editing, saved
answers, copy and export. NumPy and other approved packages load entirely
from the carried bundle.

“Existing Pyodide windows” means the current pyodide-interaktiv
pyodide-python cells: Monaco and cell controls on the page, Python already
in CTMWorker through the frontend's runCell plugin. P13 keeps and adapts
those windows; it does not build a competing IDE or replace them with
py-exercise graders. The current ZIP workflow pins frontend
16561e6604a8047027a4b053ad0d7b8e140efe7f independently of the package.
The implementation must replace that frozen override with the reviewed
P13 frontend head and synchronize its shipped ctm-libs.

Standalone math-exercise and py-exercise use that same page worker, including
pages without any pyodide-interaktiv cells. An endless checker and an endless
learner program must both be stoppable. Python source, checker imports,
custom checkers and SymPy never execute on the page thread.

**Next phase (phase 2, recorded, not implemented):** move ctm-stack's SymPy
plugin from its private publish:false CTMWorker onto this page worker, and
include STACK/Maxima assets in the offline/exam bundle. Retain its backend
adapter contract and Maxima's separate non-Pyodide engine. Phase 1 must
leave plugin registration, worker ownership and asset composition extensible
for that work; it does not require ctm-stack changes or a Maxima download.

One Python interpreter per page is the target. In phase 1:

- Ordinary IDE + math-exercise + py-exercise share one interpreter.
- A mixed STACK/SymPy page still has its private interpreter and a second
  SymPy import (K4). This is phase 2's explicit duplication.
- pyodide-interaktiv's optional interactive canvas plot upgrade can currently
  load a second main-thread Pyodide to unpickle figures. The exam IDE will
  use worker-produced PNG plots and will not activate that upgrade. Existing
  course pages that explicitly use canvas keep their current behavior and
  this additional interpreter until separately addressed. The acceptance
  report counts it; “one Python” must not hide this exception.

Workers contain CPU work; they are not an independent operating-system
memory sandbox. No promise is made that unlimited allocation cannot crash
a browser process. Output and plot delivery must themselves be bounded
(§3) so normal runaway output cannot freeze the page.

## 3. Page/worker contract and message paths

### 3.1 Ownership, startup and transactions

ctm-libs owns a single page-runtime broker. Every consumer registers its
required commands/plugins synchronously during document initialization,
before Python starts. The broker publishes the same promise/proxy through
the existing compatibility globals. A page with pyodide-interaktiv adopts
its configured plugin and startup cells; standalone pages start the core
worker without those document cells. A racing ensurePyodide call cannot
start a competing interpreter. Worker-side use of ensurePyodide still
creates the real interpreter locally in that worker; it must not recursively
spawn a worker.

A shared per-runtime transaction API serializes complete operations from
all three consumers, including setup mutations, package installs, guard
snapshot/restore, Python request globals and cleanup. A worker plugin can
perform one logical operation in one command. Existing low-level RPC
compatibility remains, but supported component operations must all use the
broker; one consumer's private queue is insufficient. Stage-2 downloads may
proceed outside Python while idle; their installs and startup Python must
take the same transaction ownership. A transaction cannot recursively wait
on itself.

Each operation has an ID, owning component/cell, and worker generation.
Results, errors, status, stream batches, plot payloads and input requests
carry the operation/generation identity. The page routes them only to that
owner. Stream/input handlers are scoped subscriptions, not shared mutable
callbacks that another component can overwrite. Results are structured
clone values or JSON; no live PyProxy or DOM object crosses the boundary.
Destroy worker-side proxies after serialization.

The broker owns queue cancellation and replacement. Every Stop invalidates
the active operation's token and cancels queued operations from that scope,
including removing worker-side queue entries before they can execute. Reject
their promises and suppress late output/results; never replay the stopped
learner operation. A successful graceful Stop retains the worker generation
only after cleanup/idle acknowledgement; new explicit Run/Check waits for that
acknowledgement. A hard restart invalidates the whole worker generation,
rejects all its pending operations and starts one replacement; new Run/Check
waits for replacement readiness. Queued checks get a retry message, never a
silent fresh-interpreter grade. A failed start can be retried; no unresolved
promises or second initialization survive a load timeout.

### 3.2 Message path by feature

| Feature | Page responsibility | Worker responsibility and reply path |
|---|---|---|
| IDE Run | Read editor, save source, submit runCell transaction; render results | Load permitted imports; execute source in the document-cell namespace; return existing serializable cell result |
| py-exercise Run/check | The existing Check action runs source and tests. Retain its public controls, fresh-namespace semantics, restrictions and scoring; submit one owned transaction | Install private runner/guard; run learner program and authored tests; restore in finally; return unchanged result/test JSON. “Run” in this design includes that execution; a separate new Run button is not required |
| stdout/stderr | Append text safely to the owning output area, with accessible status; copy/export visible output | Emit bounded batches with operation ID; preserve stream order and flush before final result; never render HTML received as plain output |
| input() | Show inline prompt/entry for the owning run, keep Stop available, validate UTF-8 length, submit/cancel through broker | Isolated: publish prompt and wait on shared buffer; page writes response and Atomics.notify. Abort wakes the wait. No isolation: immediate explained input-unavailable failure; no blocking page prompt and no invented message-only synchronous fallback |
| Plots | Display/copy/export worker-produced PNGs using existing plot presentation; release replaced object URLs | Generate plots in worker using the existing cell plugin's proven PNG path; send bounded image data. No plot unpickling via a second page interpreter in the exam IDE |
| py-exercise plots/input during Check | Route to that check's output/prompt without running code again | Factor reusable input/figure plumbing from runCell, retaining the exercise's current namespace and grading runner. Do not substitute the IDE runner for authored tests |
| math-exercise Check | Gather textual/matrix/graphical responses and settings, show busy/result UI, persist ordinary answers | Load shared checker payload/SymPy and call the same ctm-checkers JSON entry points |
| math custom checker | Send authored source and response as current request data; page retains DOM/JSXGraph operations | Execute source, helper imports and checker tests in worker; return the same verdict/score/details/feedback contract |
| Limits and Stop | Own wall-clock timers and buttons; remain available during Python execution | Shared interrupt buffer, input wake-up and graceful unwind, or termination/reinitialization (§4) |

The operation envelope also identifies the execution phase. Only the learner
program's output, figures and prompts may reach its output area. Authored
tests, reference solutions, checker setup and custom checker internals retain
private capture; they cannot publish stdout/plots or open learner input. The
existing public test-result messages remain unchanged. Preserve the current
py-exercise boundary that snapshots learner stdout before running tests.
Regression tests use teacher-only sentinel strings, figures and prompts to
prove they never enter the DOM, exported answers or learner stream.

The exam IDE's proposed output policy is text and worker-produced PNG only.
Python-produced HTML is displayed inertly as text; embedded scripts, rich
HTML and JavaScript animations are not executed in the page. Otherwise a
Python result can return a synchronous JavaScript loop and recreate the
main-thread freeze. This is an explicit AC decision (§10), not an assumed
equivalence with the existing rich-output windows. Existing ordinary course
rich-output behavior remains outside the exam responsiveness guarantee;
retain its compatibility tests and record that exception in the report.

No main-thread Python fallback is permitted if workers are unavailable or
blocked. Keep editing, saved answers and export accessible and show a clear
worker-start failure with Retry and hosting guidance.

**Output pressure:** batch stdout/stderr before postMessage, with at most
one bounded batch awaiting acknowledgement; the producer must not accumulate
an unbounded unsent queue. Preserve normal output exactly; after a documented
per-run display cap, discard further display output and show one localized
“Output truncated; Stop is still available” notice. Apply limits before
allocating the page-side DOM and before returning the exercise runner's
captured StringIO output. Plot count/encoded bytes also have explicit limits.
Do not truncate grading inputs or alter test outcomes. Exact cap values and
the capture strategy must be reviewed with the implementation, with output
flood tests proving Stop remains clickable.

The Python capture sink must enforce its budget in write(), before growing
an unbounded StringIO or formatting a huge RPC result. Slicing getvalue() is
too late. Display truncation is separate from semantic capture: if an authored
test/checker observes captured output, it must see the complete contractual
value. If a resource cap prevents that, return an explicit incomplete/resource
failure and commit no verdict or score; never grade against truncated data.

## 4. Stop, stop-after and learner-visible recovery

stop-after keeps its approved meaning: **offer Stop**, default 20 seconds,
with existing component/global overrides. It is not an automatic kill.
Loading (180-second ceiling) and queue waiting are reported separately;
the execution timer begins when the operation owns the interpreter, after
required initialization/imports. IDE controls keep their existing immediate
Stop behavior while running; slow-operation text appears at stop-after.
Do not introduce an automatic exercise timeout option in phase 1.

| Runtime capability | Stop action | Learner sees |
|---|---|---|
| crossOriginIsolated and working SAB/interrupt buffer | Request KeyboardInterrupt, abort pending input, wait up to the existing two-second grace; if Python will not yield, terminate/restart | “Stopping…” then “Stopped”. Variables remain only after successful unwind; after restart, explicit reset notice |
| No isolation/SAB, including ordinary LAN HTTP | Terminate the worker immediately; reject old generation; start one replacement | “Stopped. Python is restarting; variables and imported state were reset. Your code and saved answers are kept.” Then Loading/Ready |
| Worker startup/runtime failure | Fail pending work; offer one explicit Retry; do not loop automatic restarts | Actionable failure plus preserved editors/answers/export |

A Stop can affect the shared interpreter, so explain its page-wide scope.
Code, stored answers and completed displayed results survive. Transient
variables, files in the interpreter and imported state do not survive a hard
restart. After hard restart, document setup cells, output cells and explicitly
authored autorun:true cells rerun once from their original authored sources,
as in the existing frontend policy. Restored/edited learner source and the
stopped operation are never automatically replayed. The ordinary exam IDE
cells have autorun:false. Successful graceful Stop reruns no startup cells.
Test counters and source sentinels prove both paths preserve this distinction.
Successful interrupt cleanup restores guards/streams; if that cannot be
established, restart. Cancellation does not write a wrong verdict or zero
score or overwrite a previous completed grade. Editing during execution is
preserved and any finished result remains bound to its submitted snapshot.

Without isolation, input() is not interactive. Show this capability before
Run and a localized explanation on use (“Interactive input needs a secure,
cross-origin isolated server; use the supplied header-equipped server”).
Stop and ordinary Python still work. This explicitly supersedes step 5's
older “plain HTTP has no Stop” statement; graceful interruption and interactive
input remain isolation-dependent. An unsupported input is not a grading verdict.

## 5. Offline delivery and cross-origin isolation

The ZIP remains a complete rendered website, opened over HTTP(S), not
file://. No request outside its bundle is allowed: worker/core/plugin,
coi-serviceworker, Monaco workers, Pyodide distribution, wheels, fonts and
plot dependencies are all local. Learner code that asks for an external URL
must fail under the exam network policy; CTM itself must never fetch an
external fallback.

Use a self-hosted module worker entry and self-hosted plugin assets for the
exam/standalone path, resolved by the canonical CTM asset/dependency APIs.
Extract the embedded worker source into one canonical core; compatibility
source wrappers, if retained for existing CTMWorker callers, are generated
and checked against it. Plugins register before interpreter init from
reviewed local module URLs. The ZIP does not depend on blob: or data: for
starting Python. Existing optional blob transport must not bypass startup
failure reporting. Blob/data image/export behavior remains a separate
SEB-policy acceptance item.

Extend the **complete asset lock**, not just a loose site manifest, to cover
the exact worker core, each installed plugin and any COI service worker,
with repository/commit provenance and per-file hashes. Their installed site
locations must resolve at both root and nested paths. Use the canonical
builder/verifier to hash and carry these application assets alongside the
vendor set. Regenerate the complete lock and prebuilt receipt at the tested
set heads; the ZIP's old lock digest/run ID cannot certify changed files.
Missing, tampered or omitted worker/SW/plugin assets fail both packaging and
extracted-ZIP acceptance. No large bundle or raw evidence enters Git.

Isolation paths:

1. **Exam, preferred:** trusted HTTPS + server COOP same-origin, COEP
   require-corp, and the existing asset CORP/CORS headers. The supplied
   offline server can send them itself. An HTTPS wrapper/certificate trusted
   by the clients is still necessary for a non-localhost LAN origin.
   Headers alone on plain LAN HTTP do not create a secure context or SAB.
2. **Ordinary secure web hosting:** self-hosted coi-serviceworker may supply
   the isolation headers where the host cannot. Verify the actual runtime
   result rather than equating registration with isolation. Preserve the
   initial-UI/save barrier, deep links, subdirectory scope and the existing
   bounded reload/unavailable path. No reload loop or lost typed answers.
3. **Plain LAN HTTP or disabled SW:** use worker execution and terminate/
   restart Stop; explain input unavailability. Do not instruct SEB to adopt
   Chrome insecure-origin flags.
4. **Embedded exam resource:** probe the actual top-level/iframe deployment.
   A child cannot force an unisolated embedding page to become isolated.
   Use a top-level resource where possible; otherwise apply the observed
   degraded capabilities and test storage/copy under that configuration.

The COI service worker is a header shim, not an offline cache. Keep step 5's
HTTP-cache-only decision; server outages after reload are not covered.
Do not weaken opaque board sandboxing or enable additional external origins.

## 7. P16: measure before changing the default

Worker execution removes P16 drawback 1, “freeze without a worker”, but not
the CPU/battery/download and repeated-navigation costs. Do not infer that
idle preload is automatically the right default.

Extend integration/feedback/loading-timing.cjs and measure on the same
runner with exact candidate/baseline heads. Compare idle, interaction and
check modes for standalone math, standalone py, IDE and mixed pages, local
and CDN modes where available, cold and warm cache and a constrained-network
profile. Include ready event/time, first meaningful Check/Run, visible editor/
control readiness, first/warm execution, main-thread long-task count/total/
maximum, and bytes/package requests from before navigation. Note API gaps
where long-task observation is unavailable; do not report missing as zero.
Include a plain nonisolated worker mode, isolated mode and no-Python control.

Page-level package union includes only actually required checker/author
packages; do not force SymPy into the IDE. Save-Data keeps check/on-demand
behavior. Preserve D2's priority for interactive work over background
downloads. Status is shared (not started/loading stage/ready/failed/restarting)
with accessible localized text and no competing status owners.

First deliver measurements and a proposed default to AC. Until then, retain
current loading behavior. **The exam ZIP keeps pyodide: preload-packages:
false**, including explicit local imports on demand. Changing that opt-out
requires measurement and AC's decision. P16 setting/catalogue changes belong
to the reviewed runtime feature, not a hidden change in the ZIP fixture.
