**Scope (AC, 23 Oct).** Three ordered parts, each its own PR or stacked set:

- **Part A — port and seam.** Rename to ctm-stack; the SymPy backend fully
  on ctm-libs (settings, catalogue, shared matrix input, typesetting, Stop,
  feedback, store); and the backend contract both backends use (§8): a
  backend descriptor on the card, one plan format, the error protocol, and
  `cas:` selection at build. The Maxima backend then plugs in as M4a without
  a frontend patch.

- **Part C — H1.** `#| checker:`, `#| tests:`, `#| checker-value:` on
  ctm-checkers' `core/custom.py`; the PythonChecker v1 (`#| python-checkers:`,
  `CHECKERS`) retires without an alias (step-2 §13).

golden diff (only part C changes verdicts, and only for v1 checker files it
converts); `{.stack-question}` with `#| file:` and `#| question:` builds as
before; one Pyodide constant; no frontend branch per backend; the SymPy
backend gets no large new development (plan §8, backend roles).

**Out of scope.** The Maxima backend's production worker, engine, input
admission and board adapter (M4a, after the runtime work); one JavaScript
input admission for both backends (lands with M4a, plan §8); instant
validation (gated per backend: SymPy after S-12, plan §8 — the card keeps the
Validate button); the standalone-page worker shared with math-exercise (P13,

## 7. Runtime (part A, K4)

### 7.1 The STACK worker

`ctm-stack.js` starts one worker per page and backend through
`CTMWorker.start({plugin: CTM_STACK_SYMPY_PLUGIN, commands: {stackValidate:
[…], stackGrade: […], stackTests: […]}, publish: false, …})` (`docs/api.md:494-518`).
The plugin (worker-side source string) loads SymPy and the STACK part of
ctm-checkers (`ensureCheckers(py, CTMCheckersStack)`), installs `_ctm_guard`,
and declares three commands, `stackValidate`, `stackGrade`, `stackTests`,
which call `ctm_checkers.browser.call('stack.validate'|'stack.grade'|
'stack.tests', …)` exactly as `worker.js:89-108` does today. Nothing is
published as `mainPyodide`, so pyodide-interaktiv and math-exercise on the
same page keep their own runtime (two interpreters on a mixed page remain
until P13 — known cost, S-16).

### 7.2 Queue and stale replies

The worker's queue serialises commands (as `pipeline` does today). The card
keeps its generation counter and drops stale replies (`stack-sympy.js:505`).
New: a request superseded by a newer one *of the same card and kind* is
removed from the queue before it runs (plan F-13, cheap here).

### 7.3 Timeouts and Stop

- Loading: ctm-libs' `withLoadLimit` (180 s) applies to the worker start;
  the per-request clock starts only after loading (F-68).
- A request that runs longer than `stop-after` shows ctm-libs' Stop
  (`whenSlow`). Stop interrupts through the shared buffer on isolated pages
  and restarts the worker otherwise; the card then shows "Stopped" and keeps
  the answers. No silent 120 s kill.
- Until S-12's budgets land, a long SymPy evaluation is stopped by the
  learner or by a hard ceiling (`stack: stop-after` × 6, at least 120 s, as a
  last resort), reported as a runtime failure (§8.4).

## 8. The backend contract (part A, K5)

### 8.1 Descriptor

The Lua filter writes one descriptor per backend used on the page:

```html
<script type="application/json" class="ctm-stack-backend" data-backend="sympy">
{"id": "sympy", "version": "<ctm-checkers version>", "plugin": "<url>",
 "worker": null, "assets": ["<ctm-checkers wheel url>", "…"],
 "capabilities": {"inputs": ["algebraic", "matrix", "…"], "tests": ["AlgEquiv", "…"]},
 "requires": {"isolation": false}}
</script>
```

Each card names its backend (`data-backend="sympy"`). The frontend looks the
descriptor up, starts that backend's worker once (`plugin` for a CTMWorker
plugin, `worker` for a backend with its own worker script — Maxima in M4a)
and sends the same envelope. There is no global registry to patch and no
backend-specific branch in `ctm-stack.js`.

### 8.2 Plan format (card payload version 2)

```json
{"version": 2, "id": "…", "backend": {"id": "sympy", "planSchema": 1,
  "stackRevision": "3338304", "engine": "ctm-checkers 0.10.x"},
 "question": {"…common: inputs, display, CASText output, qtests…"},
 "variants": [{"seed": 1, "question_html": "…", "…": "…",
               "plan": {"…opaque, read only by the backend…"}}],
 "review": false}
```

- Shared parts (inputs, display per variant, feedback slots, qtests, H1
  checker, variant identity) are read by the frontend.
- `plan` per variant is opaque to the frontend and sent back with each
  request. For SymPy it is today's frozen environment; for Maxima the native
  binding (`engine.js:232-241`) plus its environment.
- `stackRevision` is the one pin (plan D3a, 4.14.0). The SymPy engine's
  reference data move to it with the ctm-checkers re-pin (plan §8 D3a);
  until then the field reports `10d3233`.

### 8.3 Envelope

Unchanged for SymPy: request `{id, type: 'validate'|'grade'|'tests',
question, variant, answers}`, reply `{id, ok: true, result}` or
`{id, ok: false, error}`. New: `error` is `{kind, code, message, detail?}`
(§8.4). The native worker's `backend` metadata field is allowed and ignored.

### 8.4 Three outcomes (plan F-3)

| Kind | Examples | Card | Session |
|---|---|---|---|
| CAS result | a test that cannot decide (S-11: false branch with a note); invalid input | normal result: `status` `invalid` with validation feedback, or a graded result | kept |
| `author` | `UnsupportedQuestion`, a malformed plan, a checker that raises | "This question has an error" with the code for the author; the learner's answer is kept | kept |
| `runtime` | load failure, worker crash, Stop, the hard ceiling | "Could not check this answer" with Retry | restarted |

ctm-checkers' `stack/page.py` (`:16-36`) already catches
`UnsupportedQuestion`; C6 makes it return `{kind: 'author', code}` and lets
everything else surface as `runtime` from the worker. Only `runtime` may
restart a worker.

### 8.5 Selection and capabilities at build

- The filter resolves `cas` per block (§4) and asks that backend to prepare
  the question (SymPy: `ctm_checkers.stack.cli render` as today).
- A question a backend cannot run stops the build with one author message
  naming file, question and construct. For SymPy the message names the way
  out when another backend could: "needs `cas: maxima`" (unsupported options
  after S-07, answer tests and functions outside the subset, and the S-03
  log/root/abs family where a question's teacher answers or tests reach it —
  plan §8).
- There is never a runtime fallback to another backend.

## 11. Part C — H1

As step-2 §13 decided (option B) and plan D4 refined:

- `#| checker:` (a `check(response, symbols)` function), `#| tests:`, and
  `#| checker-value:` (default 1) on the block. The checker is an implicit
  response tree `checker`; its score (0–1, math-exercise's normalizer) is
  weighted like `<value>` and aggregated, penalised, rounded and placed
  (`[[feedback:checker]]`) like any tree.
- Inside an XML tree: `<answertest>PythonChecker</answertest>` with
  `{"checker": "check"}` calls the block's checker as a predicate (true at
  score 1) and adds `response["node"]`; other names select library checkers
  from `ctm_checkers.matrix`.
- Implemented once, in ctm-checkers on `core/custom.py`
  (`execute_checker`), as `stack.check`; the response keys are variants
  decision 13's (`answers`, `teacher`, `variables`, `expressions`, `inputs`,
  `variant`).
- `#| python-checkers:`, `CHECKERS`, `checker_api` and `stack/checkers.py`'s
  registry retire without an alias. ctm-stack's examples and fixtures
  (`examples.qmd:200-328`, `tests/fixtures/browser/*-checkers.py`) are
  converted in the same PR, with their golden diff.
- The Maxima backend calls the same `stack.check` through its continuation in
  M4d (plan §5).
