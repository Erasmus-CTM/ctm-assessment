Read-only audit of `work/loading-lifecycle-draft.md`, canonical sources under `work/first-visit-fix`, the installed/preserved demo, installer sources, and the native Maxima engineering prototype. No browser campaign, remote write, product edit, or Maxima runtime work was performed. Consumer and shared-worker follow-up repairs are in progress elsewhere; findings below describe the inspected source and require a final source recheck after those repairs.

## JSXGraph, speech, hidden boards and containment

Installed JSXGraph `lua/jsxgraph.lua:812–838` creates a separate data-URL iframe: optional synchronous preloader → original native async MathJax script → classic JSXGraph script/CSS → assessment bridge/editor/authored board code. In ctm-libs `runtime/mathjax-opaque-adaptor.js:6–42`, opaque origin only and default startup/adaptor only are adapted. The created data worker loads the original SRE worker and mathmaps. This is neither CTMWorker nor the isolation service worker. The adaptor has no own error/timeout/retry protocol; vendor MathJax owns speech readiness. Missing speech is not evidence that Python failed.

The concrete demo's authored board handler waits on its own window load and MathJax startup (`work/demo-integration-build/pages/step4-ui.qmd:201–203`). That pattern is author code, not a guarantee imposed on all JSXGraph boards. The draft should say so. Parent MathJax startup never establishes child readiness. Lazy embedded frames (`ctm-libs/lua/ui.lua`) and hidden/revealed geometry have their own activation/layout phase; top load and initial editor construction do not prove a hidden board has drawn ink.

Math external-response Check is intentionally conditional: only a question with `responseSource` uses its iframe (`math-exercise.js:671–734`), bounded by a 5s parent timeout. JSXGraph's bridge waits up to 3s for authored registration (`jsxgraph.lua:761–787`). Failure must affect that graphical question's response, not unrelated text questions or py-exercise. No direct py-exercise → JSXGraph or speech dependency was found. Build-time missing authored `.jsxgraph` extension is rejected intentionally by `ctm-libs/lua/deps.lua:74–82`; that is distinct from browser failure after a valid render.

## Native Maxima and STACK boundary

The actual installed demo `work/demo-integration-build/.private-extensions/resolved-repos.json` and `_extensions` contain ctm-libs, math-exercise, py-exercise, pyodide-interaktiv, ctm-checkers, JSXGraph and umbrella, **no stack-sympy**. Its existing STACK checker part does not mean a STACK card/runtime was initialized.

The native engineering source is available under `work/board-weight/prototype`. `native/backend-worker.js:5,21–61` loads native JS modules/rules/messages, creates MaximaSession and awaits its readiness. `runtime/maxima-session.js:42–93` separately requires actual isolation/SAB, fetches the STACK manifest, creates buffers and a child worker, and waits for matching STACK-library ready/version with a 240s child-start timer. The manifest fetch precedes that timer. `runtime/maxima-child.js:12–35,106–173` verifies optional preload bytes/files, adapts lazy filesystem loading and starts the upstream runtime; its emitted Maxima sentinel is the real runtime ready signal. Failure poisons the session; backend recovery discards a poisoned session before a later request, without replaying the failed program (`backend-worker.js:16–19,66–96`).

`native/python-bridge.js:35–82` lazily imports CTM runtime/checker scripts and loads Python/SymPy/checker wheel only on a visited PythonChecker continuation. This is a Python interpreter in the native backend worker, not the page IDE's shared promise. Native-only grading does not wait for it. The derived engineering frontend under `work/board-baseline/engineering-parent-fresh/site_libs/quarto-contrib/stack-sympy-0.3.0/stack-sympy.js:9–118,320–346,525–580` gives each named backend an independent lazy worker pool; actual validate/grade/tests trigger startup. Parent MathJax display failure is caught separately (`:190–196`). Provenance of that derived seam is `work/board-weight/scripts/milestone-two/frontend.py:1–100`. This is prototype evidence, not current pack activation or a design commitment for the next integration.

Future Maxima readiness must remain independent of `qpyodideReady`, stage 2 and Python-authored startup. If future startup can begin before an isolation navigation, it needs an explicit COI relationship. UI readiness must not await a runtime gated by that same reload decision.

## Offline/ZIP and retained evidence

Current `coi-serviceworker.js:40–76` proxies network responses with COOP/COEP; it does not precache a site. Wheel CacheStorage (`pyodide-worker.js:301–330`) is package reuse, not an offline site contract. `scripts/serve-offline.py` is an HTTP server with exam headers/ranges/gzip, not a browser cache installer. The exact installer source's `docs/offline-install-preparation.md` explicitly labels its API private preparation and its carried input a **directory envelope only**. A complete ZIP-install/offline-SW lifecycle is absent from the audited current contract; CI/reviewer ZIPs are distribution artifacts. Do not add a completed offline/ZIP claim to the map.

`work/first-visit-probe/findings.md` and `work/resize-local/first-visit-findings.md` remain failed/limited evidence exactly as retained: static Chromium/Firefox isolation established in those runs; WebKit explicit unavailable fallback; original Chromium Matplotlib abort still unexplained; superseded-loader/retired-board missing terminals remain unknown. Headered functional success is separate. This audit supplies source evidence, not raw-clean static acceptance. Expected injected fault errors must remain in negative-case reports and must not be presented as a normal raw-clean pass.
